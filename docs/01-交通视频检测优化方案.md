# 交通摄像头检测优化方案

目标场景：道路监控摄像头（含高位俯拍）下的车辆与行人检测。

三个硬指标：

1. **预判能力** —— 判断运动物体的速度与方向，并能外推未来短时轨迹
2. **轻量化** —— 算力开销可控，能在边缘设备或单卡多路实时运行
3. **多目标准确判定** —— 密集、遮挡、小目标场景下不漏判、不串 ID

本方案把三个指标拆成可独立验证的技术面，再给出开源项目组合、实施阶段和验收指标。

---

## 一、指标拆解：要达成目标，需要动哪些环节

### 1.1 目标一：速度与方向预判

这不是单个模型能解决的事，它是一条链路，任何一环掉链子，速度数字就不可信：

| 环节 | 作用 | 缺失后果 |
|---|---|---|
| 检测 | 逐帧给出目标框 | 漏检直接丢速度 |
| 跟踪（ID 稳定） | 把跨帧目标串成同一辆车 | ID 切换 = 速度突变、方向乱跳 |
| 标定（像素→米） | 建立画面与真实世界的比例、透视关系 | 速度只有像素值，没有物理意义 |
| 滤波与运动模型 | 抑制抖动、估计速度矢量 | 数字剧烈跳变，无法用于判定 |
| 轨迹外推 | 预测未来 0.5~2 秒的位置 | 只能"看到现在"，不能"预判" |
| 业务判定 | 逆行、违停、异常变道 | 输出无法直接对接业务 |

关键结论：**速度精度的上限由标定精度决定**，不是由模型精度决定。相机接近正俯视时单应变换退化，标定的价值主要体现在视差校正和尺度换算上（这一点在本地复现 TrafficLab-3D 时已经实测到）。

### 1.2 目标二：算力轻量化

轻量化有五个可下手的地方，收益从大到小：

| 层面 | 手段 | 典型收益 |
|---|---|---|
| 模型选型 | NanoDet-Plus / YOLOX-Nano / PP-PicoDet / YOLO11n | 参数量降到 1/5~1/10 |
| 输入策略 | ROI 裁剪、动态分辨率、跳帧检测、多路共享推理 | 直接按比例省算力 |
| 精度压缩 | INT8 量化（PTQ/QAT）、结构化剪枝、蒸馏 | 速度 1.5~3 倍，显存减半 |
| 推理引擎 | TensorRT / OpenVINO / ONNX Runtime / ncnn | 同模型再提速 1.5~3 倍 |
| 后处理 | NMS-free（YOLOv10/RT-DETR）、class-agnostic NMS | 省掉后处理瓶颈 |

本机实测环境：**RTX 5060 Laptop（8 GB，算力 12.0 = Blackwell）**。
Blackwell 是新一代架构，必须用 CUDA 12.8 以上的后端；老的 cu121 编译产物会直接报"找不到可用内核"。
目前已有的 `ml` 环境已升级为 `torch 2.14.1+cu130`，GPU 实测可用。

### 1.3 目标三：多目标准确判定

分两层，优化手段完全不同：

**检测层（找得全、分得对）**
- 类别体系要和场景对齐：车 / 卡车 / 公交 / 摩托 / 自行车 / 行人
- 小目标与密集场景：提高输入分辨率、切片推理（SAHI）、小目标增广
- 类别混淆：**这是实测坑**——COCO 预训练权重把正俯拍的轿车识别成 "cell phone"（置信度 0.92），必须用交通场景（如 VisDrone）微调权重

**关联层（跟得稳、不串号）**
- 跟踪器：ByteTrack（两声部关联，几乎零额外算力）/ OC-SORT（抗遮挡）/ BoT-SORT + 相机运动补偿
- 代价矩阵：IoU + 运动预测 + 可选轻量 ReID
- 参数：`track_buffer`、`match_thresh`、`new_track_thresh` 必须按场景标定
- **实测坑**：TrafficLab-3D 的配置里写了 `tracker_type: bytetrack`，但调用时没有传给 ultralytics，实际跑的是 BoT-SORT，导致示例视频里两辆车丢了一辆；修复后轨迹数从 1 条变 6 条

## 二、样本处理：投入产出最高的一环

模型再改，不如数据对。样本侧有六件事：

1. **场景对齐**：训练集必须覆盖目标相机的安装角度。俯拍数据和街景数据不是一回事，域差会直接摧毁精度
2. **公开数据集打底**
   - VisDrone：无人机俯拍，车辆、行人、密集小目标，和监控视角最接近
   - UA-DETRAC：道路监控车辆检测与跟踪
   - MIO-TCD：交通目标分类
   - BDD100K：多天气、多时段行车视角
3. **自动标注 + 人工复核**：用开放词汇模型（YOLO-World / Grounding-DINO）+ 分割模型（SAM2）生成初标，人工只做修正，标注成本可降一个数量级
4. **难例挖掘**：夜间、雨天、逆光、遮挡、超小目标单独建集，训练时加权
5. **增广策略**：Mosaic、小目标 copy-paste、运动模糊、透视扰动、亮度/色温扰动
6. **固定评测集**：自建 200~500 帧人工精标，任何改动都在这上面量指标，否则优化无从判断

### 3.2 两个可选组合

**组合 A：快速可用（内部/开源项目适用）**

```
检测   ultralytics YOLO11n/s（交通场景微调）
跟踪   ByteTrack（ultralytics 内置）
标定   TrafficLab-3D 的单应矩阵流程
运动   自研 Kalman / IMM 速度方向估计
可视化 supervision
部署   ONNX → TensorRT / OpenVINO
```
优点：生态成熟、上手快、和已有复现成果直接衔接。
代价：ultralytics 是 **AGPL-3.0**，如果封装成软件对外分发，按协议要求需要开源整个衍生作品。

**组合 B：可闭源商用（Apache/MIT 系）**

```
检测   NanoDet-Plus 或 YOLOX-Nano（交通场景微调）
跟踪   OC-SORT / ByteTrack（MIT）
标定   自研（MIT）
运动   自研 Kalman / IMM
部署   ONNX Runtime / TensorRT / OpenVINO / ncnn
```
优点：全链路宽松许可，可闭源交付。
代价：训练与调参工作量大一些，没有 ultralytics 那种一条命令搞定的体验。

### 3.3 组合后的系统架构

```
视频输入
   │
   ├─(可选) ROI 裁剪 / 动态分辨率 ──── 省算力
   │
   ▼
检测器（轻量 YOLO，INT8）──────────── 目标：找得全、分得对
   │
   ▼
跟踪器（ByteTrack / OC-SORT）──────── 目标：ID 稳定
   │
   ├─→ 标定模块（单应矩阵，像素→米）
   │
   ▼
运动估计（Kalman / IMM）───────────── 目标：速度矢量 + 航向角
   │
   ├─→ 短时轨迹外推（0.5~2 s）─────── 目标：预判
   ├─→ 业务判定（逆行/违停/异常变道）
   │
   ▼
输出：结构化 JSON + 实时画面叠加 + 事件推送
   │
   ▼
封装：CLI / HTTP 服务 / 桌面 GUI / Docker
```

### 3.5 最终融合链（准入后）

**运行时串联（数据流）**

```
检测（ultralytics；闭源场景换 edgeyolo/PaddleDetection）
  → 小目标切片（SAHI，按需开启）
  → 跟踪（boxmot 提供的 ByteTrack / OC-SORT）
  → 标定与运动估计（自研：单应矩阵 + Kalman）
  → 轨迹外推与业务判定（自研：速度/方向/逆行/违停）
  → 可视化与统计输出（supervision）
```

**离线训练链路**：CVAT 标注 → FiftyOne 数据集管理与难例挖掘 → Autodistill 自动预标注 → ultralytics / PaddleDetection 训练

**部署链路**：ultralytics 内置导出 → TensorRT（NVIDIA）/ OpenVINO（Intel）/ MNN（端侧）/ ONNX Runtime

**评测链路**：py-motmetrics（MOTA/IDF1）+ 自研速度/方向误差评测

**自研模块（刻意不引外部依赖）**：标定、测速、方向判定、轨迹外推、逆行与违停判定。
这几块是业务核心，且公开项目普遍不成熟（见上表），自己实现反而更可控。

**许可证冲突提示**：ultralytics 与 boxmot 均为 AGPL-3.0。
若最终软件要闭源分发，替换路径为：检测换 Apache-2.0 的 edgeyolo 或 PaddleDetection，跟踪按公开论文自行实现（算法本身不受限），
标注、数据集、评测工具本身即为 MIT/Apache，无冲突。

## 六、已知风险

1. **标定精度**：正俯视时单应退化，速度只能保证趋势；倾斜安装视角下效果最好
2. **TensorRT 兼容性**：RTX 5060 是 Blackwell，需要 TensorRT 10.13+；否则退到 ONNX Runtime CUDA 或 OpenVINO
3. **域差**：公开数据集与实拍画面差异大，最终必须用实拍数据微调
4. **许可证**：ultralytics 的 AGPL-3.0 对"软件封装分发"有实质约束，需尽早确定交付形态
5. **8 GB 显存**：训练只能用小模型 + 小批量，或使用梯度累积 / 混合精度
