# 19 · 项目亮点的表达：场景先验预计算

日期：2026-10-07。用户问："我的项目亮点是那个预计算运用，不知道怎么体现和与实际接轨。"

本文给出**定位 → 证据 → 演示脚本 → 落地形态 → 报告写法**五段，全部基于已经跑出来的实测数据。

---

## 一、先把亮点说准

现在代码里这套东西叫"静态目标地图/隐标记"，但它真正的技术价值比名字大得多。
建议按下面的口径对外表述：

> **亮点名称：场景先验预计算（Scene Prior Precomputation）——把"不变的部分"从在线推理里剥离。**
>
> 监控摄像机是**长期不动**的，场景里大量结构（路桩、标志牌、信号灯、路灯）位置固定。
> 主流做法（包括我们用的 ultralytics 生态）是**每一帧重新检测**，于是这些结构会被
> 反复漏检：一辆公交开过、一个行人走过，柱子就从画面上消失了。
> 我们的做法是：**离线**用多帧投票 + 语义校验把这些不变的东西固化成一份"场景先验"，
> **在线**只做一次查表注入。

一句话对比：

| 主流做法 | 我们 | 
|---|---|
| 每帧独立检测，漏了靠跟踪补 | 离线固化先验，在线直接注入 |
| 提精度靠**加算力**（更大模型、更高分辨率、切图） | 提精度靠**搬算力**（把贵的部分搬到离线） |
| 换机位/换场景要重新调 | 每个机位产出自己的先验文件 |

**注意**：这不是"换个界面"或"调个参数"，是**在检测器之外单独设计了一层**——
它有自己的观测累积、一致性判据、遮挡判定、语义校验和增量更新逻辑，
这正是评审规则里"自主设计突出、有明确创新"要的东西
（规则同时写明"仅调用通用模型接口、直接部署现有开源项目不算创新"，所以这层自研是必需的）。

## 二、可核验的效果数据（已实测）

对照实验：取预计算地图**确认保留**的 113 个静态位置（6 段视频），
逐帧检查"如果关掉地图，主检测器这一帧能不能检出它"：

| 指标 | 数值 |
|---|---|
| 机会总数（位置 × 帧） | 33,900 |
| 关掉地图时主模型命中 | 2,109 次 = **6.2%** |
| 开启地图后 | **接近 100%** |
| **结论** | **约 94% 的帧，静态结构本来会消失或被漏掉** |

配套的"防误检"数字（这也是亮点的一部分——先验不能乱标）：

| 环节 | 数值 |
|---|---|
| 跨帧投票候选簇 | 每段 51~79 个 |
| 一致性 ≥80% 确认 | 每段 19~33 个 |
| **CLIP 语义校验后保留** | 每段 14~23 个（**否掉 52 个"位置稳但认错"**的候选） |
| 过小碎片拦下 | 3,142 个 |

CLIP 那一步的典型反例（都来自实测）：把**花坛路缘石**当路桩、把**红色广告牌**当标志牌、
把**建筑立面**当路灯。这类错误只有"看框外的上下文"才能判出来——
这正好呼应了用户当时提的"对周遭物体考量不清晰"。

## 三、怎么在演示视频里"看得见"（3–5 分钟脚本）

评审看的是"能否一眼看懂你的创新"。建议按下面的顺序剪：

| 时间 | 画面 | 要打的字 |
|---|---|---|
| 0:00–0:30 | **问题**：同一段视频，一辆公交驶过，路桩/标志牌在画面上消失；再放一次慢动作 | "每帧独立检测：被挡住就丢" |
| 0:30–1:20 | **预计算过程**：位置清单逐条出现（编号 + 类别 + 观测一致率），CLIP 校验把"广告牌/路缘石"标红否掉 | "离线：多帧投票 + 语义校验" |
| 1:20–2:20 | **效果对比**：左右分屏，左边关地图、右边开地图，同一段视频同步播放 | "静态结构可用率 6.2% → ≈100%" |
| 2:20–3:20 | **完整产品**：输入视频 → 输出带预判的视频（四档梯度、低置信标注、遮挡续推） | 产品能力展示 |
| 3:20–4:20 | **效率**：离线阶段（每 3 帧一次开放词汇检测 + CLIP）vs 在线阶段（查表注入），给出耗时对比 | "贵的算一次，快的天天用" |
| 4:20–4:50 | **增量维护**（可选）：新加一根路桩，下一次预计算自动纳入 | "场景变了，只需重算一次先验" |

**拍摄要点**：左右分屏那 60 秒是全片最有说服力的一段，务必用同一段素材、同一帧对齐。
（这段的素材可以直接从现有输出里生成：`outputs/diag02k_nms050/`（开地图）
与 `outputs/nomap_check/`（关地图）就是同一批视频的两版结果。）

## 四、与实际接轨：落地形态

### 1. 目标场景（先验天然成立的地方）

路口监控、园区/厂区卡口、停车场出入口、工地、校园门口——
共同点是**摄像机长期固定**，场景结构几个月不变，正是"预计算"最划算的场合。

### 2. 部署形态：一次预计算，长期在线用

```
【离线·每机位一次】                       【在线·实时】
 视频样本 → 多帧投票 → CLIP 语义校验  →   scene_prior.json  →  逐帧推理（只加载查表）
  （贵：开放词汇检测 + CLIP）              （几十 KB）           （便宜：无第二个模型、无 CLIP）
```

这同时**解决了我们刚测出的性能问题**：当前默认流程因为在线也跑第二个模型 + CLIP，
比之前慢约 6 倍（0.09 → 0.53 秒/帧）。把预计算挪到离线、结果缓存成文件后：

- 在线速度回到 ~0.09 秒/帧（30 秒素材约 1 分钟出片）
- 边缘设备（算力弱的盒子、工控机）也能跑，因为在线不需要开放词汇模型和 CLIP
- 预计算可以放在夜间/空闲时段跑，不占实时链路

### 3. 维护与增量

- 同一机位长期使用：先验文件可复用；光照/季节变化大时可定期（如每月）重算一次
- 新增/移走的路桩、换掉的广告牌：下次预计算自动更新，**人工只需审"位置清单"**
  （几十条），不必逐帧——这正是"人工复核很难逐帧"的现实条件下最可行的复核形态
- 误检风险由 CLIP 语义校验 + 人工位置清单双重把关

### 4. 对客户讲的价值

| 客户痛点 | 预计算给出的答案 |
|---|---|
| "柱子有人走过就没了" | 静态结构可用率从 6% 提到 ~100% |
| "边缘设备带不动大模型" | 贵的部分移到离线，在线只查表 |
| "场景里东西太多，逐个标太贵" | 复核粒度从"每帧几十框"降到"每个类几十个位置" |
| "系统上线后场景变了怎么办" | 重跑一次预计算即可，人工只审位置清单 |

| 评分项 | 这一段怎么写 |

## 六、把它拆成两条命令（**已完成，2026-10-08**）

> 本节原为"建议立刻做"的规划；现已实现并实测，命令与实测数字更新如下。
> 早期版本这里写的是 `trafficvision.precompute --video` 与 `--prior`，与最终实现不一致，已更正。

离线与在线已彻底分离：

```bash
# ① 离线预计算（每个机位只跑一次；可以一次喂多段同机位视频，投票更稳）
python -m trafficvision.precompute \
    --videos 机位A_1.mp4 机位A_2.mp4 机位A_3.mp4 \
    --camera 路口A \
    --out outputs/scene_prior/路口A.json

# ② 在线推理（加载先验，跳过扫描与语义校验；也可用默认的 --scene-prior auto
#    让同一机位首次运行自动落盘、后续自动命中）
python -m trafficvision.cli --video 待处理.mp4 --horizon 1 --out 结果.mp4 \
    --scene-prior outputs/scene_prior/路口A.json
```

**实测（VID_112222，120 帧）**：

| | 耗时 | ms/帧 | 来源 | 确认位置 | 注入框 |
|---|---|---|---|---|---|
| 首次（现场计算） | 38.1 s | 318 | scan | 13 | 1367 |
| 第二次（命中缓存） | **9.7 s** | **81** | cache | 13 | **1367（逐位一致）** |

离线预计算本身也实测通过：单段 120 帧 → 候选 53 → 投票确认 15 → 语义校验否掉 3 → **写出 12 个位置**。

三个好处都已兑现：

1. **亮点显性化**：演示就是"一个先验文件 + 两条命令 + 一张速度对比表"；
2. **性能问题一并解决**：在线不再跑第二个模型和 CLIP，回到原始基线（约 81 ms/帧）；
3. **复用价值可讲**：先验文件是跨视频、跨项目可移植的产物，且**两次运行输出逐位一致**，
   证明"先验固化"这一步是无损的（对应"开放成果"分）。
